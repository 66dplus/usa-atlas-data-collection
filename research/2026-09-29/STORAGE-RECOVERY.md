# Восстановление после повторного запуска компактизации

Дата: 2026-09-29. Эта заметка относится к разрешённому обслуживанию существующей `usa_atlas` в контейнере `usa-atlas-postgres`. Она не даёт указания заменять действующую БД или изменять соседний Supabase. Проверка ниже выполнена чтением каталога, файлов и кода; работающий runner не менялся.

Автоматические тесты не добавлялись и не запускались. Для этого этапа использовались статическое чтение/AST кода, read-only catalog queries и `EXPLAIN` без `ANALYZE`; точное сравнение production данных выполняется самим разрешённым maintenance process.

## Два разных backup

Первый полный архив создан 2026-09-28 до построения новых таблиц. После прерывания первого процесса у него не оказалось привязки metadata к исходному fingerprint, необходимой для автоматического повторного использования. Повторный запуск с `--renew-unbound-backup` сохранил прежний checkpoint и начал новый `pg_dump` под maintenance/source locks.

Первый архив сохранён здесь:

```text
/srv/usa-atlas/maintenance/20260928-compact/
  unbound-backup-20260929T134650159420Z/
    usa-atlas-before-compact.dump
    backup.json
    source-fingerprint.json
```

Размер первого архива: **592 524 948 байт**. SHA-256 из metadata после первоначального чтения всего архива через `pg_restore`:

```text
b30486aa3a945de4eb7f8e8fd54ab329809ae97c09bab7824dec914d31c6c808
```

В архивированном `backup.json` поле `path` осталось историческим: оно указывает на прежнее имя файла в родительском каталоге. После перемещения искать этот архив нужно **внутри указанного `unbound-backup-*` каталога**. Его размер и hash относятся к первому архиву, а не к создаваемому сейчас файлу с прежним именем.

Второй архив успешно создан и прочитан полностью; размер **929 358 558 байт**. Его рабочий путь:

```text
/srv/usa-atlas/maintenance/20260928-compact/usa-atlas-before-compact.dump
```

Команда использует `pg_dump --schema=usa_atlas`, поэтому новый снимок включает **исходную таблицу и уже построенные объекты компактизации**:

- исходную `observation` с 49 206 438 ранее проверенными строками;
- `observation_data`, `source_resource`, `methodology`;
- временный проверочный view `observation_compact_check`;
- catalog, ingests, schema metadata и staging.

Это полноценный backup промежуточного состояния обслуживания, а не чистой v1 или окончательной v2. Он может быть больше первого архива. Наличие `.dump` ещё не означает готовый backup: `backup.json` появляется после успешного `pg_dump`, полного чтения архива и расчёта SHA-256. Привязка `source_fingerprint_sha256` добавляется после повторного вычисления исходного fingerprint под теми же locks.

## Почему повторный запуск безопасен

По состоянию каталога на начало второго запуска `observation` остаётся физической таблицей. В новой `observation_data` сохранены PK и все три индекса; `indisvalid` и `indisready` равны true. Четыре FK, добавлявшиеся в долгой lock-транзакции прошлого запуска, откатились вместе с ней. Runner вновь создаёт и валидирует их через ту же сессию, которая владеет locks исходных родительских таблиц.

Проверка данных второго запуска началась полностью заново. Для точного сравнения отключены parallel workers и parallel hash, которые ранее упирались в shared memory контейнера. Сравниваются все 13 полей каждой строки; предел временных файлов — 16 GiB. Вчерашние семь записанных диапазонов в `exact-validation.json` не доказывают завершения сегодняшнего запуска: смотреть текущий `progress.json`, `complete` и итоговый `result.json` вместе.

В ходе независимого чтения обнаружен отдельный недостаток границ: в фактической `en_US.utf8` collation символ `:` сортируется перед цифрами. Поэтому прежний последний диапазон `geo_id >= ':'` повторял почти всю таблицу. Пробелов в проверяемом множестве это не создаёт, но делает последний join слишком большим. `EXPLAIN` без выполнения запроса показал полный Hash Join; отключение hashjoin даёт два полных Sort примерно по 49 млн широких строк и также не решает риск временного диска. Безопасное исправление требует монотонных границ `None, 00, …, 99, None`. Повторное использование уже проверенных диапазонов допускается только с привязкой к неизменившимся исходному и compact fingerprints под locks, совпадающими counts и нулевыми расхождениями. Этот текст фиксирует обнаружение; сам по себе он не подтверждает применённое исправление или завершение проверки.

Все четыре файла staged code совпали с SHA-256 из `staging-manifest.json`. На момент чтения production `schema.sql` и `load.py` оставались v1. Самостоятельно переключать их во время работающего обслуживания не требуется: этим управляет runner под loader locks.

Лёгкая проверка зависимостей не нашла внешних FK, пользовательских триггеров, наследования или внешних view/routine dependencies для исходной `observation`. Обнаруженные CHECK constraints принадлежат самой таблице. `DROP TABLE` в cutover не использует `CASCADE`: неожиданная новая зависимость должна вызвать ошибку и откат транзакции, а не удаление зависимого объекта.

## Как использовать новый backup для отката

Сначала восстановить архив в отдельной изолированной PostgreSQL 16 среде. Не применять команды удаления к работающей production БД по этой заметке.

1. Сверить SHA-256 именно выбранного архива с его собственной metadata и полностью прочитать архив. Для первого архива учитывать перемещение файла.
2. После восстановления подтвердить, что исходная `observation` является таблицей, а её counts, ключи, значения и provenance соответствуют сохранённому baseline.
3. Если восстановлен второй архив и требуется получить чистую v1, после проверки зависимостей убрать **только** восстановленные вспомогательные объекты: `observation_compact_check`, затем `observation_data`, `source_resource`, `methodology` и принадлежащие им sequences/indexes. Сначала подтвердить наличие и целостность исходной `observation`. Это действие относится к изолированной restore-среде.
4. Сопоставить восстановленную схему с сохранёнными `schema.sql.v1` / `load.py.v1`. Проверка v1 catalog pin до удаления промежуточных объектов ожидаемо не пройдёт, хотя исходные данные присутствуют.
5. Только после успешной проверки восстановленной среды отдельно планировать переключение приложения и БД. Ранний backup и исходные normalized/raw артефакты сохранять до подтверждения исправного чтения UI и следующего обновления.

Если новый запуск снова остановится, `--renew-unbound-backup` допускает создание свежего снимка только после получения maintenance/source locks. Проверенный и правильно привязанный backup переиспользуется лишь при совпадении hash архива и fingerprint; изменившийся исходный fingerprint вызывает отказ. Не дописывать привязку к старому архиву вручную.

## Точный checkpoint для исправления последнего диапазона

Добавлен отдельный одноразовый `database/capture_exact_checkpoint.py`. В этом обслуживании он запущен root под systemd для старого PID `841908`. Он ожидает именно старую фазу `range_index=101`, `lower=":"`, `upper=null`; произвольные текущие запросы не отменяет. Перед сигналом он проверяет PID/start time исходного процесса и handles трёх maintenance/loader locks, существование одного PostgreSQL владельца advisory lock и блокировок всех девяти исходных/новых таблиц, проверенный backup и оба fingerprints. В packet сохраняются полные fingerprints, их SHA-256, backup SHA-256, counts, OID таблиц и индексов, PK/view definition, завершённые диапазоны и identity конкретного backend. Затем отменяется только активный повторный tail-запрос с тем же PID и digest SQL. Старый runner самостоятельно откатывает свою транзакцию и освобождает locks.

Packet находится вне Git:

```text
/srv/usa-atlas/maintenance/20260928-compact/exact-resume-checkpoint.json
```

Guard сохранил packet и успешно отправил отмену только backend `487725` **2026-09-29 14:48:20 UTC**. В packet записаны counts `49 206 438` с обеих сторон, 101 завершённый старый диапазон (из них 100 пригодны к переиспользованию), SHA второго backup `220986156c37684c43ffa8d532d4c52799e03c6546372424fc864f0543059ca0`. SHA самого packet: `a30ca3e641eb1f5d4f82dc51f12d0321200babbe264e361c14139f87b5b62827`. Старый процесс затем вышел; root подтвердил освобождение его PostgreSQL locks перед запуском продолжения.

После завершения старого процесса root запускает разрешённое продолжение:

```bash
python3 database/cleanup_storage.py compact --apply \
  --resume-exact-checkpoint /srv/usa-atlas/maintenance/20260928-compact/exact-resume-checkpoint.json
```

Это строгий режим существующей полной shadow: он запрещает новый backup, copying, построение таблиц/индексов/словарей. Он заново получает maintenance/loader/source locks и блокирует shadow со словарями; проверяет OIDs и определения существующих объектов, готовность трёх индексов, PK, все ingest counts и SHA полного backup. Затем повторно вычисляет **оба полных fingerprints**. Продолжить можно только при совпадении с сохранённым packet и друг с другом. Откатившиеся FK заново создаются и валидируются владельцем locks.

Переиспользуются только 100 точно проверенных непрерывных диапазонов `[−∞,00)`, `[00,01)`, …, `[98,99)` с `mismatches=0`. Старый `[99,':')` отбрасывается; исправленный `[99,+∞)` проверяется заново. Итог — 101 диапазон и все прежние 13 полей, без выборочного сравнения. Отдельная запись в окончательном `exact-validation.json` связывает результат с SHA packet.

Порог свободного диска в этом режиме — **30 GiB**: 12 GiB исходного резерва, до 16 GiB временных файлов проверки и 2 GiB дополнительного запаса. Снижение относительно обычных 74 GiB допустимо только потому, что режим запрещает новый backup, recopy и построение индексов. Обычный режим сохраняет прежний порог. Если complete shadow, packet или bound backup отсутствуют, продолжение завершается ошибкой; оно не подменяется новым построением.

Первое строгое продолжение завершило все 101 диапазон без расхождений, но в **15:03:20 UTC** откатило cutover: у извлечённого `CATALOG_DOCUMENT_SQL` отсутствовал финальный `;`, поэтому последующий служебный `SELECT` marker стал синтаксической ошибкой. Исходная таблица сохранилась, production code восстановлен в v1. Исправлен только разделитель SQL в `LockedSession.query`: перед marker теперь всегда добавляется отдельный `;`. Неуспешный запуск сохранён в `failed-resume-20260929T150429Z/` внутри maintenance state, включая его exact/fingerprint evidence и приватные диагностические логи. Следующее строгое продолжение опять должно получить locks и заново сверить оба полных fingerprints. Сам по себе успешный data comparison из откатившегося запуска не означает завершённую миграцию.

Для повторного полного fingerprint разрешены три parallel workers плюс leader в пределах квоты контейнера 4 CPU. Это session settings только двух fingerprint queries; parallel hash отключён. `EXPLAIN` без выполнения данных подтвердил малые aggregate/sort по source и, для compact view, два обычных hash словарей примерно 1.1 MB суммарно на процесс. Точное сравнение диапазонов по-прежнему выполняется последовательно с `max_parallel_workers_per_gather=0`. Глобальные PostgreSQL/role settings не менялись.

После успешной независимой проверки выполнен **один** последовательный read-only inventory query в согласованном snapshot, с ограничениями 30 минут / 128 MB work_mem / 16 GiB временного диска. Он завершился в **15:23:39 UTC**, за **247.955 секунды**. SQL и результаты сохранены в [production-coverage.sql](production-coverage.sql) и [production-coverage.json](production-coverage.json).

- В production действительно **49 206 438 строк**, но заполнено **31 из 81 поля каталога**; ещё 50 не имеют observation rows. Подробные distinct geo_id и диапазоны period даны по каждому полю/source/geo_type в JSON.
- Census ACS содержит **48 175 437 строк** для восьми демографических полей `01.01–01.08`, period `2024`, на уровнях state/county/place/tract. Tract coverage — 85 382 geo_id для `01.01–01.05` и 84 401 для `01.06–01.08`.
- **Строк уровня block group в этом production snapshot нет.** Собранные новые файлы вне admission pipeline этим аудитом не считаются загруженными в БД.
- Общее число строк включает множество field_id серий и margins of error внутри одного поля; оно не означает 49 млн отдельных тем. Distinct geo_id разных полей нельзя складывать в число уникальных территорий.
- Существующие USDA food observations сохранены вместе с прочими данными; этот inventory ничего не собирает и не изменяет.
