# Хранение и обновление USA Atlas: что сокращать и что сохранять

Дата аудита: 2026-09-28. После расширения доступа обнаружена и измерена **существующая production БД** в контейнере `usa-atlas-postgres` (PostgreSQL 16.14), с данными `/srv/usa-atlas/postgres`. Она не была видна через отсутствующий локальный `psql` и localhost:5432; этот порт принадлежит отдельному Supabase и не используется этой работой.

Актуальное измерение: БД **63 944 301 591 байт**, из них `observation` **63 936 045 056 байт**: таблица/TOAST 49 579 335 680, индексы 14 356 709 376. В 9 завершённых ingest заявлено **49 206 438 строк**, включая Census 48 175 437 строк, добавленных 2026-09-22. Это действующая БД, а не устаревший checkout manifest. Источник: [postgres-before-cleanup.json](postgres-before-cleanup.json).

По разрешению пользователя **удалены 7 проверенных несжатых дублей Census**, освобождено 1 750 405 логических байт; gzip и sidecars сохранены. [Акт удаления](plain-duplicate-cleanup.json).

Запущен отдельный процесс полной компактизации повторяемых URL и методик с backup, проверками и совместимым read view. На момент запуска этого обновления процесс создаёт backup; **экономия в действующей БД ещё не объявляется достигнутой**. Фактический статус, запуск и восстановление описаны в [CLEANUP-OPERATIONS.md](CLEANUP-OPERATIONS.md). После завершения появится `postgres-cleanup-result.json` с реально освобождёнными байтами.

Ниже сохранены исходные измерения ограниченного окружения и обоснование политики. Формулировка «БД не измерена» в первом проходе относится только к нему и заменена результатами production-аудита выше.

## 2. Где найдена повторяемость

В [schema.sql](../../../database/schema.sql) нет колонки `slug`. Строки `field_id`, `catalog_field_id`, `geo_id` — стабильные идентификаторы, которыми связаны сборщик, загрузчик и UI. UI формирует дополнительные slug-подобные ID в `usa-atlas-design-lab/scripts/atlas_data.py`; их не следует удалять из публичного контракта.

Повторяемые URL и описания действительно записаны в каждую `observation`. На двух доступных файлах измерено:

| Источник / поле | Строк | Уникальных значений | UTF-8 байт значений во всех строках | UTF-8 байт уникальных значений |
|---|---:|---:|---:|---:|
| EIA `source_url` | 310 | 1 | 39 990 | 129 |
| EIA `methodology_note` | 310 | 5 | 3 100 | 50 |
| EIA `retrieved_at` | 310 | 1 | 9 920 | 32 |
| FBI `source_url` | 3 266 | 364 | 323 332 | 36 036 |
| FBI `methodology_note` | 3 266 | 2 | 129 220 | 71 |
| FBI `retrieved_at` | 3 266 | 1 | 104 512 | 32 |

URL и методика вместе занимают 495 642 байта содержимого строк. Их словари содержали бы 36 286 байт содержимого уникальных строк: **459 356 повторных текстовых байт** в этих JSONL. Это показатель повторяемости, а не экономия PostgreSQL: потребуется место для внешних ключей, таблиц и индексов. Для `retrieved_at` разница особенно существенна: JSON хранит текст, а существующая БД уже хранит `timestamptz`.

Потоковое gzip-сжатие полных неизменённых JSONL в памяти, уровень 6, дало EIA 3 435 байт и FBI 46 737 байт — вместе **50 172 байта вместо 1 504 151**. Это проверенный кандидат для файлового архива. Исходные fixtures не менялись, новый архив не подменял manifest. В PostgreSQL такого коэффициента обещать нельзя: TOAST обрабатывает достаточно крупные значения/строки, он не заменяет словарь повторяющихся коротких значений между строками. [PostgreSQL 16: TOAST](https://www.postgresql.org/docs/16/storage-toast.html).

Есть семь пар `full/raw/full/census_acs/group-*.json` и `.json.gz`, содержимое которых после распаковки побайтно совпало: B01001, B03002, B05001, B05002, B05005, B05006, B25070. Несжатые файлы занимают **1 750 405 байт**, сжатые — **138 977 байт**. Это конкретные кандидаты на удаление дублирующей несжатой копии после проверки ссылок и восстановления. Текущий `cached_payload()` для Census выбирает `.gz`; старые файлы могут быть нужны старой ревизии сборщика. Они сейчас оставлены.

У 139 raw payloads проверены SHA-256 sidecar и `binding.payload_sha256`: несовпадений нет. Их 139 `.sha256` занимают 9 035 байт, а 139 `.binding.json` — 61 438 байт. **Сохранять все 70 473 байта:** это подтверждение корректности resume, а не ненужные метаданные. Проверка содержимого payload не означает, что binding совместим с текущей ревизией кода; это отдельно проверяет сборщик.

## 3. Политика хранения

| Что | Решение | Почему и условие |
|---|---|---|
| Значение, исходная единица, период, география, стабильный ID ряда | Сохранять | Без них невозможно сравнение, обновление и воспроизведение |
| Географическая система, vintage границ, исходный GEOID | Сохранять / добавить явно | ZIP не равен ZCTA; county/tract/block group требуют правильных ключей и границ |
| MOE, estimate type, denominator, suppression/quality flags | Сохранять при наличии; добавить модель отсутствия | Отсутствие или подавление не равно нулю; MOE нельзя удалить как «служебное» |
| `source`, `source_release`, `unit`, `field_id`, `catalog_field_id` | Вынести в словари с короткими FK | Сохранить прежние текстовые ID через представление/API |
| `source_url` | Вынести в ресурс/запрос | Одна ссылка на реальный ресурс с параметрами без секретов, повторно использовать FK |
| `methodology_note` | Вынести в версионированную методику | Методика зависит от ряда/релиза и иногда от строки; варианты должны различаться |
| `retrieved_at` | Вынести в provenance после проверки постоянства | В текущем сборщике это timestamp нормализации источника, не доказательство времени HTTP-загрузки |
| `ingest_run`, artifact/contract/code/config/plan hashes | Сохранять | Идемпотентность, расследование расхождений, откат и регулярный refresh |
| Полный contract JSON | Хранить один раз на версию/поле | 81 строка — низкий приоритет; связь с историческим контрактом нужна дольше текущей версии |
| Raw успешных опубликованных релизов | Архивировать с проверкой восстановления | Для всех ещё опубликованных исторических данных должен оставаться воспроизводимый архив |
| Raw активного/прерванного запуска | Сохранять локально вместе с sidecars | Не потерять resume и не повторять платные/ограниченные запросы |
| Normalized JSONL | Сжатый архив вне PostgreSQL | В БД храним значения и provenance; архив нужен для переимпорта и проверки hashes |
| Точные дубли raw JSON + gzip | Удалять копию после условий из §2 | Не удалять единственный payload, sidecars retained payload или используемый старым запуском файл |
| Staging | Очищать после подтверждённого завершения загрузки | Только под тем же lock и при отсутствии активного ingest; пустая таблица может ещё занимать страницы |
| Логи, промежуточные failed normalized output | Ограниченное хранение | После разбора сбоя, завершения нового запуска и подтверждения, что файл не участвует в resume |
| Старые релизы | Политика продукта, не автоматическое удаление | История нужна для трендов, корреляций, проверки ревизий; latest-only необратимо ограничивает анализ |
| Индексы | Оценить по размерам и реальной нагрузке | PK/FK и UI запросы важны; `idx_scan=0` после сброса статистики не доказывает ненужность |
| Git history | Отдельная задача | Удаление файла из HEAD не освобождает историю; переписывание истории потребует отдельного решения |

Практичная начальная политика: локально держать текущий и предыдущий успешные релизы плюс все активные checkpoints. Для более старых опубликованных релизов хранить проверенный сжатый архив raw, normalized, контрактов и manifests в хранилище артефактов. Срок хранения логов можно начать с 30 дней, но сохранять логи неразобранных ошибок до закрытия инцидента. Это предлагаемая политика, сейчас она не применена.

В FBI `methodology_note` прямо говорит, что coverage сохранён в raw. Удалить raw без извлечения coverage и проверенного архива — потерять объяснение полноты наблюдения.

## 4. Конкретный компактный контракт v2

Это проект для отдельной миграции, не DDL, который уже применён. Нормализованный обменный формат v1 и физический формат БД могут различаться: загрузчик способен принимать старые JSONL, раскладывая метаданные по словарям.

| Таблица | Минимальные поля / ключи |
|---|---|
| `provider` | `provider_id smallint PK`, `code text UNIQUE` |
| `catalog_field` | существующий стабильный `catalog_field_id`, label; ссылка на версию контракта |
| `contract_version` | `contract_sha256`, полный документ/неизменяемый URI, `plan_sha256`, `config_sha256`, `collector_sha256` |
| `series` | `series_id integer PK`, `field_id text UNIQUE`, `catalog_field_id FK`, `provider_id FK` |
| `release` | `release_id integer PK`, `provider_id FK`, `source_release text`, явная дата публикации/порядок релиза |
| `series_release` | `series_release_id integer PK`, `series_id FK`, `release_id FK`, `unit_id FK`, `definition_version`, estimate type, denominator/MOE relation; UNIQUE(series, release) |
| `geography` | `geography_id bigint PK`, `namespace`, `geo_type`, `geo_id text`, `boundary_vintage`, parent FK при применимости; UNIQUE(namespace, type, id, vintage) |
| `period` | `period_id integer PK`, исходный `period text`, start/end, frequency; для ACS также окно 5-year |
| `source_resource` | `resource_id bigint PK`, sanitized URL, request/body fingerprint при POST, upstream artifact hash/URI и format |
| `method` | `method_id integer PK`, неизменяемый текст/definition hash и версия |
| `ingest_run` | существующие идентичность/статус/время плюс ссылка на `contract_version` и manifest hash/URI |
| `provenance` | `provenance_id bigint PK`, `ingest_id FK`, `resource_id FK`, `method_id FK`, точный прежний `retrieved_at`; повторные комбинации переиспользуются |
| `observation_fact` | `geography_id bigint FK`, `period_id integer FK`, `series_release_id integer FK`, `value double precision`, `provenance_id bigint FK`, `quality_flags` при наличии; UNIQUE(geography, period, series_release) |

Нужно поддержать несколько raw ресурсов для производного значения: `provenance_resource(provenance_id, resource_id, role)` вместо предположения «строка всегда получена из одного HTTP-ответа». Флаг `source_geo_id`/namespace позволяет сохранить исходный код провайдера и отдельно отображать canonical GEOID. Строковые FIPS сохраняют начальные нули; длина кода без типа и vintage недостаточна для идентичности.

Самое узкое обязательное ядро факта — пять полей `geography_id`, `period_id`, `series_release_id`, `value`, `provenance_id`. Конкретные типы surrogate keys выбираются после оценки кардинальности; менять бизнес-идентификаторы ради нескольких байт не требуется. Hash как 32-byte `bytea` вместо 64 hex символов допустим в будущем, но ingest/catalog маленькие — это не первый источник экономии.

Методика, единицы и релиз должны иметь неизменяемую версию. Изменение определения ряда не должно незаметно переписывать смысл старых значений. URL нельзя просто укоротить до homepage: фильтры API и версия ресурса являются частью происхождения. API keys и персональные credentials исключаются, как уже делает `validate_record()`.

## 5. Совместимость UI и регулярный refresh

Текущий UI жёстко читает `usa_atlas.observation`, `catalog_field`, `ingest_run`. В `scripts/atlas_data.py` используются `geo_id`, `geo_type`, `period`, `field_id`, `catalog_field_id`, `value`, `unit`, `source`, `source_release`, `source_url`, `methodology_note`, `retrieved_at`, `ingest_id`. API возвращает source URL, методику и timestamp; простое удаление колонок сломает интерфейс. Каталог также требует ровно 81 поле с согласованными именами.

Первый вариант миграции — физическая `observation_fact` и совместимое read-only view `usa_atlas.observation`, восстанавливающее все прежние колонки JOIN-ами. UI получает тот же JSON. Старую функцию `finish_ingest()` необходимо заменить новым загрузчиком/транзакцией: она вставляет прямо в `observation`, а view с несколькими JOIN не является заменой таблицы для этого кода.

**Существующий загрузчик пока не реализует обычный периодический refresh.** `_load_database_locked()` проверяет существующую БД через `assert_complete_state(admissions)`: нужны точное совпадение общего количества строк, списка ingest и всех artifact hashes с новым manifest. Поэтому изменённый артефакт на непустой БД отклоняется до `load_admission()`, несмотря на `ON CONFLICT` в SQL. Исторические ingest тоже нарушат текущую проверку полного совпадения. Перед плановым обновлением нужен отдельный refresh contract.

Предлагаемая последовательность refresh:

1. Сформировать immutable `release + contract_version + ingest_manifest`, скачать/проверить raw и normalized hashes; сохранить checkpoint.
2. Подтвердить ожидаемое покрытие и ключи для конкретного источника/географического уровня. Частичный ответ не может стать опубликованным релизом.
3. Загрузить в staging; проверить cardinality, дубликаты, диапазоны, единицы, suppression, географию и ссылки provenance. Сравнить с предыдущим релизом и объяснить большие сдвиги.
4. Транзакционно опубликовать релиз и изменить указатель `published_snapshot`. Для исправленного того же релиза хранить revision/supersedes; не считать лишь совпадение label доказательством идентичности.
5. Сохранить предыдущий снимок для отката. Повторный артефакт с тем же hash — no-op. Проверять целостность выбранного snapshot, а не требовать удаления всех исторических ingest.
6. Сопоставить ответы старого view/API с исходным форматом: canonical keys, значения, периоды, единицы, URL, методика, отсутствие и тип географии. Для state/county поведение UI должно сохраниться.
7. Открыть tract/block-group только отдельным обновлением UI/геометрии. Сейчас `canonical_geo()` и SQL отфильтровывают всё кроме state/county; появление более глубоких строк в БД не сделает их видимыми автоматически.

Текущий UI выбирает snapshot по строковому `period DESC, source_release DESC`. При введении нескольких релизов следует использовать явный порядок публикации, сохранив правило «один период/релиз для всей карты, без подстановки старого значения для отдельного места».

## 6. Порядок внедрения и условия удаления

1. Запустить [audit_storage.py](../../../database/audit_storage.py) на действующем сервере: получить реальные таблицы, индексы, число/возраст ingest и выборку повторяемых полей. Не принимать решение о размере БД по этому checkout.
2. На копии данных построить минимальные словари URL/методик и полную v2, измерить размеры всех таблиц **вместе с индексами** и время API. Принимать вариант по результату, а не по проценту сжатия JSONL.
3. Подготовить восстановимый backup и архив manifests/raw/normalized. Восстановить выборку и проверить hashes. Отдельно подтвердить, какие snapshots/артефакты больше не участвуют в resume и rollback.
4. Выполнить отдельную версионированную миграцию со старым read contract и новым writer, обновить pin schema hash и проверки `database/load.py`. Текущий код отклоняет произвольное изменение схемы — это ожидаемо.
5. После сравнения результатов и успешного refresh удалить только утверждённые дубли и staging. Для семи пар Census достаточно сохранить canonical gzip + его sidecars, но сначала проверить manifest/код и восстановление нужной ревизии. Ничего не удалять из активного checkpoint.
6. Повторно измерить физическое место. `DELETE` обычно освобождает место для повторного использования внутри таблицы. `VACUUM FULL` переписывает таблицу, требует дополнительного диска и сильной блокировки; это отдельная операция с окном обслуживания. Не запускать её автоматически. [PostgreSQL 16: VACUUM](https://www.postgresql.org/docs/16/sql-vacuum.html).

Не удалять WAL/каталоги PostgreSQL руками. Аудит различает database/table/index размеры, но не измеряет общий WAL, replication slots, backups и object storage; если сервер занят ими, потребуется отдельная диагностика на сервере.

Из корня `usa-atlas-data-collection`:

```bash
python3 database/audit_storage.py > /tmp/usa-atlas-local-storage-audit.json
# На сервере с установленным psql и заранее настроенным libpq:
python3 database/audit_storage.py --postgres > /tmp/usa-atlas-server-storage-audit.json
# Или только SQL, без сканирования локальных normalized-файлов:
psql -X -w -qAt --dbname usa_atlas --set ON_ERROR_STOP=1 -f database/audit_storage.sql
```

Python ничего не удаляет и не меняет исходные файлы; JSON пишет в stdout. Соединение фиксировано на `usa_atlas`, пароль не запрашивается, `.psqlrc` отключён. SQL содержит только чтение, `BEGIN READ ONLY`, локальные timeout settings и `ROLLBACK`; он не создаёт extension, таблицы или индексы. Ошибки подключения выводятся кодом без stderr/credentials. `--postgres` при отсутствии доступа сохраняет `postgres.status=not_measured`; это не успешное измерение БД.

Инвентарь использует `pg_table_size`, `pg_indexes_size`, `pg_total_relation_size` по их определению в [PostgreSQL 16: system administration functions](https://www.postgresql.org/docs/16/functions-admin.html). Число строк из planner/statistics оценочное. Выборка — 1% страниц с фиксированным seed, максимум 100 000 строк; она может быть пустой и не является равномерной выборкой строк. Размеры текстовых полей внутри выборки — логические, их нельзя вычитать из размера relation как готовую экономию. Значения полей, URL, учётные данные и строки пользователей в отчёт не выводятся.

Локальное сканирование читает все normalized JSONL; максимум 200 000 уникальных строк на поле удерживается в памяти. При превышении лимита `distinct_exact=false`, уникальное число становится нижней границей, потенциальная повторяемость в байтах не вычисляется. Для больших артефактов это bounded-cardinality аудит, а не полноценная проверка дубликатов ключа. Schema/admission/provenance validators остаются отдельными обязательными проверками.

Аудит реально выполнен `2026-09-28T17:26:33Z`; результаты записаны в JSON. Дополнительными проверками подтверждены точные суммы строк/байт, совпадения hashes присутствующих fixtures, отчёт об отсутствии шести normalized-артефактов, семь идентичных после распаковки пар, переход `distinct_exact=false` при лимите 1, обработка отсутствующего `psql`, read-only параметры запуска клиента, скрытие stderr с тестовой секретной строкой и отклонение manifest path за пределами `full/`. `git diff --check` завершился без ошибок.
