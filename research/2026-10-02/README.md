# Покрытие 81 показателя и объём БД — 2 октября 2026

## Что означает «собрано»

Проверка выполнена против действующей `usa_atlas` через индексные запросы к
`usa_atlas.observation_data`. «Есть» означает хотя бы одну числовую строку
исходного ряда для показателя и типа географии. Это **не** обещание полного
покрытия всех штатов, готовности вычисленной доли/рейтинга или доступности в
интерфейсе. Подавленные значения лежат отдельно в quality records и не
считаются числовыми наблюдениями.

- [Все 81 показателя и восемь географических уровней](catalog-coverage.csv).
  Повторить снимок: `docker exec -i -u postgres usa-atlas-postgres sh -c
  'exec psql -X -w -q --csv -P footer=off --username "$POSTGRES_USER" --dbname
  usa_atlas --set ON_ERROR_STOP=1' < database/field_coverage.sql`.
- [Все 43 набора pipeline](dataset-coverage.csv). Для 22 observation datasets
  `*_rows` — число принятых строк последнего снимка, не число уникальных
  географических объектов. Остальные 21 набора — source records, которые ещё
  нельзя приравнивать к готовому показателю.
- [Прямая связь исходных материалов с пятью незагруженными показателями](raw-evidence.csv).
- [Аудит до переключения индекса](storage-audit-before.json) и
  [аудит после](storage-audit-after.json), сделанные только чтением через
  `python3 database/audit_storage.py --postgres-container`.

## Результат

| Состояние показателя | Количество |
|---|---:|
| Есть числовые строки хотя бы на одном уровне | 46 |
| Нет числовых строк | 35 |
| Всего в каталоге | 81 |

Глубочайший **загруженный** уровень среди 46 показателей: block group — **19**,
tract без block group — **7**, county без tract — **5**, state без county —
**10**, ZIP — **3**, точка мониторинга — **2**. ZIP и monitor — отдельные типы
географии, их нельзя трактовать как census tract/block group. Двадцать два
набора observations состоят из 21 таблицы ACS и CDC PLACES; 15 наборов
содержат block groups, все 22 содержат tracts. Количество наборов и количество
каталожных показателей различаются, поскольку одна таблица питает несколько
показателей.

Семь показателей еды/супермаркетов исключены из новой работы. Три старых
показателя USDA (`09.01`–`09.03`) уже есть в БД на уровне county и сохранены;
четыре (`08.01`–`08.03`, `08.06`) не имеют числовых строк. Поэтому если
исключить всю эту группу, результат — **43 из 74** с числами и **31 из 74**
без них.

Из 35 без числовых строк пять имеют связанные source records или справочные
записи (`04.08`, `07.02`, `07.05`, `07.06`, `07.07`), но ни одна из них не
допущена как соответствующий числовой показатель. У оставшихся 30 прямая
связь с загруженным исходным набором не обнаружена в этом инвентаре.
Это определение «не затронуто» относится к текущей БД и не отрицает
возможность заметок/исследований в репозитории. Состояния 35 по контракту:
19 `blocked_access`, 7 `definition_required`, 6 `source_required`, 3
`license_required`.

## Место и сжатие

До переключения индекса вся БД занимала **105 807 027 223 байта** (98.5 GiB). Таблица
`observation_data` с индексами — **104 912 478 208 байт**: основная таблица
39 364 837 376, индексы 65 536 729 088. Из индексов lookup занимает
40 147 918 848, primary key 23 799 627 776, индекс `ingest_id`
1 589 182 464 байта. `generic_record` занимает около 838 MiB.
`pg_stat_user_tables` показывает около 185.75 млн живых и 0 мёртвых строк
`observation_data` после autovacuum. Это оценка статистики, не доказательство
нулевого bloat; `VACUUM FULL` без отдельного измерения не обещает экономии и
потребовал бы долгой блокировки и дополнительного места.

Уже действует структурное сжатие: `source_url` и `methodology_note` хранятся
по одному разу в словарях `source_resource`/`methodology`. При миграции
29 сентября оно уменьшило тогдашнюю таблицу с индексами с 63.94 до 17.79 GB
без потери 49.2 млн строк. Нынешний рост связан главным образом с загрузкой
новых 185 млн строк, а не с возвратом длинных URL в каждую строку. Срез
`storage-audit.json` показывает полные URL из **view**, поэтому их суммарные
длины в выборке нельзя трактовать как физические байты таблицы.

Индекс `observation_lookup_idx` перестроен **2 октября в 08:20 UTC**:
`CREATE INDEX CONCURRENTLY` создал индекс с теми же четырьмя ключами поиска,
без четырёх `INCLUDE` колонок. После проверки `indisvalid=true` и
`indisready=true` старый индекс удалён через `DROP INDEX CONCURRENTLY`, новый
получил прежнее имя. Повторяющиеся ключи теперь дедуплицируются; запросам,
которым нужны значения, PostgreSQL может понадобиться прочитать heap. Для
точечного запроса `01.01`/state/`06` `EXPLAIN` показал `Index Scan using
observation_lookup_idx`, а чтение вернуло значение.

Размер lookup индекса уменьшился с **40 147 918 848** до **1 738 964 992**
байт. Повторный аудит измерил **67 398 073 367 байт** для всей БД:
освобождено **38 408 953 856 байт** (около 35.8 GiB). Основная таблица
сохранила размер 39 364 837 376 байт; общий размер её индексов теперь
27 127 775 232 байта. Таймер `usa-atlas-auto-pipeline.timer` остался активен;
состояние pipeline при проверке — `complete`, но последний цикл завершился
в 08:15 UTC, до переключения индекса.
Индекс PK нужен для `ON CONFLICT` при обновлении, а индекс `ingest_id` — для
lifecycle pipeline; их не удалять вслепую.

Следующий потенциальный этап — вынести часто повторяющиеся `source`,
`source_release`, `unit` и, возможно, `field_id` в справочники с числовыми
ключами. Он требует отдельной миграции таблицы, view, ingest-кода, индексов и
точной сверки всех строк. Подрезание символов в `geo_id`, FIPS, `field_id`
или округление значения исказит данные и не является компрессией.

Вне PostgreSQL `full/runtime` занимает около 3.2 GB. Уже работает
`ops/auto_pipeline_retention.py`: после семи дней он удаляет только принятые
сгенерированные payloads с проверкой receipt/manifest/SHA, сохраняя исходники
и журнал. WAL PostgreSQL и старые backup не удаляются вручную.

`database/schema.sql` остаётся прикреплённым SHA к действующему pipeline;
операционное переключение индекса оформлено отдельной миграцией, чтобы не
сломать pin автоматических загрузок. При новом развертывании schema DDL нужно
согласованно обновить вместе с schema manifest и loader pin.
